# Testing（测试门禁与功能防退化规范）

本文件定义 VelaLoom 如何设计、编写、执行和记录测试。测试不是功能完成后的可选动作，而是功能交付的门禁和长期防退化机制。任何新增功能、缺陷修复、接口变化、数据格式变化或高风险重构，都必须根据本文件补充或更新测试。

功能门禁由可执行、可重复的验证结果构成，包括自动化测试、集成/端到端测试以及适用的语法、静态、构建和数据安全检查。README、`CHANGELOG.md`、`PROGRESS.md` 等文档用于说明和追踪交付，不属于测试门禁，不能用于替代失败或缺失的测试。

测试必须跟随开发阶段执行。一个 Issue 不得采用“全部实现完成后再统一测试”的方式；每个阶段完成最小实现后，必须立即执行该阶段测试并通过，才能继续后续阶段。

## 1. 测试目标

测试必须同时回答以下问题：

1. 新功能是否按需求工作；
2. 原有功能是否仍然工作；
3. 错误输入、边界条件和重复执行是否安全；
4. 输入数据、输出格式和用户接口是否保持约定；
5. 未来修改是否会在功能退化时尽早失败。

测试通过只说明已覆盖的行为通过，不代表未覆盖的行为天然安全。未覆盖的重要行为必须记录为风险或后续任务。

## 2. 测试分层

### 2.1 静态和快速检查

每次代码变更至少执行适用项目：

- Python 语法编译：`conda run -n VelaLoom python -m py_compile ...`；
- 测试发现和执行：`conda run -n VelaLoom python -m unittest discover -s tests -v`；
- `git diff --check`；
- 适用的 lint、类型检查、构建或命令行 `--help` 检查。

快速检查适合在编辑过程中频繁执行，但不能代替端到端测试。

### 2.2 单元测试

单元测试验证单个函数或清晰的逻辑分支，重点覆盖：

- 参数解析和输入校验；
- 映射、过滤、命名和统计逻辑；
- 空集合、重复值、非法值和边界值；
- 错误类型、错误消息和返回码。

单元测试应快速、确定、无外部服务依赖，并避免读取仓库中的大数据文件。

### 2.3 集成测试

集成测试验证模块之间的真实接口，例如脚本与 `rosbags` 的读写、目录扫描、临时文件替换和命令行调用。涉及文件格式或数据转换的功能，至少需要一个最小结构等价的集成夹具。

### 2.4 端到端和真实数据验证

高风险数据处理功能应执行端到端验证：输入数据经过完整命令后，检查输出可读、关键字段正确、未映射字段保持不变、统计结果正确，以及输入文件未被修改。

真实大文件验证成本较高时，可分为：

- 每次测试：最小可重复夹具，作为自动门禁；
- 发布前或重大变更：真实数据 dry-run 或抽样转换；
- 无法执行时：记录数据规模、未执行原因、替代验证和风险，不得默认为通过。

## 3. 测试门禁等级

| 等级 | 触发场景 | 必须通过的门禁 |
| --- | --- | --- |
| L0 | 文档或非执行文件 | `git diff --check`；链接/格式检查（如适用） |
| L1 | 纯逻辑、参数或小范围修复 | 语法检查、相关单元测试、完整 `tests/` 测试 |
| L2 | 文件、rosbag、目录批处理或公共接口 | L1 + 集成/端到端夹具 + 输入保护和错误路径测试 |
| L3 | 数据格式、破坏性操作、核心流程或大范围重构 | L2 + 真实数据验证/抽样 + 兼容性检查 + 人工复核 |

开发者必须选择不低于变更风险的等级。不能以“测试运行时间较长”为理由降低门禁；应使用分层执行或补充快速夹具。

## 4. 防止功能退化的规则

### 4.1 回归测试必须跟随修复

- 每个缺陷修复都必须先能由测试复现，修复后测试通过；
- 测试名称应描述被保护的用户行为，而不是只描述内部实现；
- 不得删除失败的回归测试来让测试套件变绿；若行为确实改变，必须同步更新需求、测试和文档；
- 对曾经发生过的严重问题，测试应保留为长期门禁，不依赖临时手工验证。

### 4.2 公共行为优先于实现细节

测试应检查用户可观察结果：输出文件、消息字段、统计、返回码和错误行为。除非接口明确要求，不要把私有函数调用顺序、临时变量名或内部类结构作为测试契约，避免重构造成无意义的测试破坏。

### 4.3 关键不变量

数据转换和批处理测试至少考虑以下不变量（按功能适用）：

- 输入文件只读，转换失败不会留下伪装成完整输出的文件；
- 未映射 topic/字段保持原值；
- 输出消息数量、时间戳和连接信息不被意外改变；
- 重复运行不会无提示覆盖已有结果；
- `--dry-run` 不创建或修改输出文件；
- 递归扫描不会重复处理输出目录生成物；
- 显式 `--overwrite` 才允许覆盖，并且输入仍不可被覆盖。

## 5. 测试夹具和测试数据

- 测试代码统一放在仓库根目录 `tests/`；共享脚本放在 `scripts/`，不得把可执行测试放入 `urdf/` 或 `rosbag/`；
- 优先在测试运行时创建最小夹具，测试结束自动清理；测试产生文件的位置必须遵守下述 `test_output/` 规则；
- 夹具应包含足够验证结构的消息/文件，并明确每个字段用于验证什么；
- 不把大型真实 rosbag、个人路径、凭据或敏感数据提交为测试夹具；
- 若必须使用仓库已有数据，测试应可检测文件缺失，并在记录中说明依赖；
- 测试必须可重复：固定输入、明确排序、避免依赖当前时间、网络、机器用户名或并发顺序；
- 时间戳、随机数和临时目录应通过可控方式生成，断言不要依赖脆弱的完整日志文本。

### 5.1 测试输出目录强制规则

- 所有开发测试和验证主动生成的文件必须写入当前仓库根目录 `test_output/`，其绝对位置为 `<repo-root>/test_output/`；
- 适用范围包括但不限于：运行时夹具、临时 bag、转换后 bag、日志、报表、决策文件、截图、渲染结果、哈希清单、失败诊断文件和中间输出；
- 禁止把测试输出写入系统 `/tmp`、`/private/tmp`、操作系统默认临时目录、`rosbag/`、`urdf*/`、源码目录或仓库外个人路径；历史文档中的旧 `/tmp` 记录只表示过去事实，不再构成允许用法；
- 测试代码使用 `TemporaryDirectory`、`mkdtemp` 或同类 API 时，必须显式将父目录设为 `<repo-root>/test_output/`；不得依赖系统默认临时目录；
- 每个 Issue 或测试模块应使用独立子目录，例如 `test_output/issue-016/`、`test_output/test_unify_rosbag_tf/`，避免并行或重复运行互相覆盖；
- 测试只可清理由本次运行创建且已精确解析的子目录或文件，不得递归删除整个 `test_output/`，也不得删除其他测试或用户保留的输出；
- 测试开始前由测试或执行命令安全创建所需子目录；测试成功或失败后均应清理不需要保留的临时文件，需要人工复核的产物可以保留，但必须在测试记录中列出；
- Python 字节码、coverage、pytest、构建系统等可配置缓存也应优先重定向到 `test_output/`；无法重定向的工具缓存必须已被 `.gitignore` 排除，并在测试记录中说明；
- `test_output/` 是本地开发产物目录，必须由根目录 `.gitignore` 排除，不得把其中的大 bag、日志或临时工件提交到 Git；
- 最终测试记录必须写明使用的 `test_output/` 子目录、保留文件和清理结果。

## 6. 测试执行规范

### 6.1 环境

非 ROS 项目测试、脚本、构建和依赖检查在 `VelaLoom` conda 环境中执行：

```bash
mkdir -p test_output/tmp test_output/pycache
TMPDIR="$PWD/test_output/tmp" \
PYTHONPYCACHEPREFIX="$PWD/test_output/pycache" \
conda run -n VelaLoom python -m unittest discover -s tests -v
```

若使用其他测试工具，必须记录完整命令和所需依赖。依赖缺失时先确认是否属于项目环境问题；不能把系统 Python 的结果当作项目门禁结果。

需要 ROS1/ROS Noetic runtime 的操作必须在 Docker 容器 `ros1_noetic` 中执行，例如：

```bash
docker start ros1_noetic
docker exec ros1_noetic bash -lc \
  'source /opt/ros/noetic/setup.bash && rosbag info <mounted-workspace-path>/rosbag/input.bag'
```

执行前用 `docker inspect ros1_noetic` 确认 `<mounted-workspace-path>`；输出文件和日志必须写入 `<mounted-workspace-path>/test_output/`，确保宿主机对应文件位于仓库根目录 `test_output/`。测试记录必须注明使用的是 `VelaLoom` 还是 `ros1_noetic`，以及宿主机与容器内的对应输出路径。

### 6.2 执行顺序

建议按以下顺序缩短反馈时间：

1. 语法和静态检查；
2. 正在修改模块的单元测试；
3. 相关集成/端到端测试；
4. 完整 `tests/` 测试套件；
5. 真实数据、性能或人工复核（适用时）。

最终交付前必须重新执行所有适用门禁，不能只引用开发中间阶段的旧结果。

### 6.3 失败处理

- 任何失败测试都必须定位原因：代码缺陷、测试缺陷、环境缺失、数据问题或已知外部阻塞；
- 未定位的失败不能标记为通过；
- 暂时跳过测试必须写明原因、影响、替代验证和恢复计划；
- 只有在外部条件确实无法解决时，才将 Issue 标记为 `BLOCKED`；
- 修复测试本身时，必须确认它仍然能在目标缺陷出现时失败，避免“空断言”或过度放宽断言。

## 7. 测试记录模板

每个完成的 Issue 在 `PROGRESS.md` 中记录至少以下内容：

```markdown
## <Issue 编号> 测试记录（YYYY-MM-DD）

- 测试等级：L0/L1/L2/L3
- 变更范围：
- 新增或更新测试：
- 测试夹具：
- 执行环境：`VelaLoom`
- 验证命令：
- 结果：通过 / 失败 / BLOCKED
- 覆盖行为：
- 未覆盖行为和风险：
- 遗留动作：
```

最终回复还应说明测试是否完整执行、是否使用真实数据、依赖是否新增，以及工作区中哪些本地变动不属于本次交付。

## 8. 标记 DONE 的测试条件

功能只有在满足以下条件后，才能依据 [`DOD.md`](DOD.md) 标记为 `DONE`：

- 选定了与风险匹配的测试等级；
- 新功能或缺陷修复有自动化测试保护；
- 相关测试和完整测试套件均通过；
- 关键不变量和失败路径已验证（适用时）；
- 测试命令、结果、未覆盖范围和遗留风险已记录；
- 不存在未解释的失败、跳过或环境依赖。

## 9. 变更隔离要求

- 每个特性测试必须与一个模块绑定；不得通过顺手修改其他模块来“修绿”测试；
- 测试文件不得留下 `TODO`、空断言或永久跳过项；无法覆盖的情况必须记录为风险或 Issue；
- 测试记录应注明提交流程：特性分支开发和验证（无提交）→ `main` 最终提交。
