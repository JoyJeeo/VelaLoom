# AI 开发工作流

## Issue 原则

`TASK.md` 是唯一任务清单。每个开发单元必须选择一个 Issue，完成该 Issue 后才能开始下一个 Issue。

不同 Issue 不可以并行执行。项目同一时刻只能有一个 Issue 处于 `IN_PROGRESS`，当前 Issue 完成或明确阻塞后，才能开始下一个 Issue。

## 变更范围和提交原则

- 一个特性或修复只允许修改一个模块；测试、文档和 `CHANGELOG.md` 是该模块的配套文件，不得借此捆绑其他模块的改动；
- 一个提交只交付一个特性或一个修复，不得把无关格式化、清理或临时调试混入提交；
- 开发前创建 `codex/<issue>-<short-name>` 特性分支，所有实现、测试和本地验证在该分支上进行；
- 特性分支只承担开发隔离，不在特性分支创建提交，也不向特性分支推送；
- 完成 DOD 验收后切换到 `main`，在 `main` 上完成暂存和提交；只允许推送 `main`，不得推送特性分支；
- 工作区有用户既有修改时，必须先记录并隔离，不能通过切换分支、暂存或提交覆盖这些修改。

### 分支操作模板

```bash
git switch -c codex/issue-xxx-short-name
# 在特性分支开发、测试和验证
conda run -n VelaLoom python -m unittest discover -s tests -v
# DOD 通过后，只在 main 提交和推送
git switch main
git status
git add <当前特性文件>
git commit -m "feat: <特性描述>"
git push origin main
```

## 执行步骤

1. 阅读本目录规范和仓库 `AGENTS.md`，尤其是 `DOD.md`、`TESTING.md` 和本文件的分支/提交规则。
2. 在 `TASK.md` 中找到一个 `TODO` Issue，将其改为 `IN_PROGRESS`；确认没有其他 Issue 正在执行。
3. 检查 `git status`，保留已有用户修改。
4. 确认使用 `VelaLoom` 环境。
5. 先确定方案、文件边界和验收标准；确认只涉及一个模块，并创建特性分支。
6. 使用 `apply_patch` 编辑文件。
7. 按 `TESTING.md` 选择与风险匹配的测试等级，执行语法检查、自动化测试或真实数据验证。
8. 按 `DOD.md` 逐项核对完成条件；满足后将 Issue 改为 `DONE`，否则改为 `BLOCKED` 或继续开发，并记录变更文件和验证结果。
9. 更新 `PROGRESS.md` 和 `CHANGELOG.md`；重要技术选择追加到 `DECISIONS.md`。`CHANGELOG.md` 是每个特性或修复必需的交付记录，但不作为测试通过的依据。
10. 确认特性分支没有提交，切换到 `main`，只提交当前特性相关文件；按授权范围推送 `main`。

## 阶段化开发和自动推进

一个 Issue 必须拆分为可验证的连续阶段，实行“实现一小段、测试一小段、通过后再继续”的门禁流程。禁止先一次性写完全部实现，再在最后集中测试。

### 标准阶段

1. **需求阶段**：拆分目标、边界、验收标准和风险；产出可执行的阶段清单。
2. **接口/方案阶段**：确定模块边界、输入输出、错误行为和测试夹具方案；先验证关键假设。
3. **最小实现阶段**：只实现当前阶段所需的最小功能，不提前堆积未验证的后续代码。
4. **阶段测试阶段**：立即执行当前阶段对应的单元、集成或端到端测试，并检查静态质量。
5. **阶段验收阶段**：核对当前阶段出口条件，记录命令和结果；通过后自动进入下一个阶段。
6. **整体回归阶段**：所有阶段完成后执行完整测试套件、适用的真实数据验证和 DOD 检查。
7. **交付阶段**：更新 `PROGRESS.md`、`CHANGELOG.md` 和必要文档，最后按分支提交规则交付。

### 阶段推进规则

- 每个阶段必须有明确的进入条件、输出物、测试命令和通过标准；
- 当前阶段测试通过后，开发应自动继续下一个阶段，不等待无关的再次确认；
- 当前阶段测试失败时，停止推进，先定位并修复当前阶段问题，再重新执行该阶段测试；
- 阶段失败不能通过跳过测试、降低断言或把问题留给最终回归来绕过；
- 阶段之间保留可运行状态，避免长期处于“半成品全部不可验证”的状态；
- 阶段记录应写入工作计划或 `PROGRESS.md`，至少包含阶段状态、验证命令和结果。

## 跨对话交接

### 用户结束当前对话时

当用户明确说“结束本次对话”“先到这里”“下次继续”等结束意图时，在结束回复前更新 `SESSION_HANDOFF.md`。记录本次对话的：

- 目标和用户确认的要求；
- 已修改的文件和已完成的 Issue；
- 关键接口、参数、路径和技术决策；
- 执行过的命令、依赖安装和验证结果；
- 未完成事项、阻塞原因和下一步动作。

### 用户开启新对话时

当用户明确说“开启新对话”“继续上次工作”等接手意图时，先读取 `SESSION_HANDOFF.md`，再读取 `TASK.md` 和 `PROGRESS.md`。恢复上下文后，向用户简要确认接手的目标和当前状态；不要重复已完成的修改或验证。

如果交接记录与当前工作区实际状态不一致，以工作区文件和最新 git 状态为准，并在继续开发前修正记录。

## 状态定义

- `TODO`：尚未开始。
- `IN_PROGRESS`：当前正在执行。
- `BLOCKED`：因明确外部条件无法继续，必须记录阻塞原因。
- `DONE`：验收标准全部满足。

## 交付要求

最终说明必须包含：完成内容、修改文件、验证命令及结果、依赖安装、提交所在分支、遗留问题和未纳入的本地变动。
