# Definition of Done（功能完成定义）

本文件定义 VelaLoom 一个开发功能、Issue 或修复可以标记为 `DONE` 的最低标准。它是 AI 开发和人工验收共同使用的交付门禁；“代码已修改”“本地可以运行”或“测试曾经通过”本身都不等于完成。

## 1. 适用范围

以下工作均必须满足本定义：

- 新增功能、命令行参数或数据转换模式；
- 修复缺陷、行为回归或兼容性问题；
- 测试、脚本、构建配置和项目规范的结构性变更；
- 影响用户操作方式、输出格式、数据安全或性能的文档变更。

纯文字拼写修正可以只执行文档相关检查，但仍应说明验证范围。

## 2. 必须满足的完成条件

### 2.1 需求和范围

- Issue 的目标、边界和验收标准已经明确；
- 实现内容与当前 Issue 一致，没有把无关需求混入同一次开发；
- 所有验收标准都有可核验的证据；
- 若需求存在歧义、外部依赖或无法验证的部分，必须标为 `BLOCKED` 或记录为明确遗留项，不能直接标记 `DONE`。
- 变更只涉及一个模块；测试、文档和 `CHANGELOG.md` 仅作为该模块的配套交付。
- Issue 已拆分为连续的开发阶段，每个阶段都有明确出口条件和对应验证证据。

### 2.2 实现质量

- 代码位于正确的目录，遵守 `AGENTS.md`、`ARCHITECTURE.md` 及相关接口约定；
- 正常路径、空输入、错误输入、重复执行和边界条件有合理行为；
- 不破坏输入数据、已有接口或既有用户工作流；数据转换类功能默认保持输入只读；
- 失败时返回明确错误或非零退出状态，不静默吞错；
- 临时文件、输出文件和资源句柄在成功与失败路径均得到处理；
- 不引入硬编码的本机绝对路径、凭据、真实数据副本或无关生成文件。
- 可执行模块的文件头必须说明 Purpose、Input、Output 和至少一个可运行 Example；
- 不得把 `TODO` 留在待交付代码中；未完成事项必须转为 Issue 或明确 `BLOCKED`。

### 2.3 测试门禁

- 新功能至少有一个自动化测试；缺陷修复必须有能复现原问题的回归测试；
- 测试放在 `tests/`，测试夹具使用最小、可重复、可清理的数据；不得依赖未声明的个人环境状态；
- 测试覆盖成功路径以及与功能风险直接相关的失败或边界路径；
- 测试通过命令必须明确记录，并在 `VelaLoom` conda 环境中执行；
- 既有测试套件和受影响的脚本检查必须全部通过；
- 测试失败、跳过或因环境缺失而未执行时，不得声称功能已完成，除非明确标记为 `BLOCKED` 并记录原因。
- 每个实现阶段都必须在进入下一阶段前完成对应测试；最终一次性测试不能替代阶段测试。

### 2.4 数据和安全验证

涉及 rosbag、文件或批处理时，还必须验证：

- 输入文件在执行前后内容或 SHA-256 未被意外改变；
- 输出目录、重名、覆盖、递归扫描和中断恢复行为符合约定；
- 不会因输出目录嵌套在输入目录中而重复处理生成文件；
- 真实数据验证若成本过高，至少使用结构等价的最小夹具，并说明真实数据未执行的范围；
- 不输出敏感数据、完整大文件或不必要的日志。

### 2.5 文档和可操作性

- 用户可从 README 或对应文档找到用途、参数、输入输出和最小运行示例；
- 新增或改变的命令行参数、默认值、覆盖策略和限制已记录；
- 重要技术选择追加到 `DECISIONS.md`，进展和验证追加到 `PROGRESS.md`；
- 测试命令、依赖和已知限制可被下一位开发者复现。
- 受影响模块的文档页或 README 已同步；

`CHANGELOG.md` 必须作为每个特性或修复的交付记录，记录变更内容及原因。它不是功能正确性的证明，也不替代任何测试；缺少 changelog 记录表示交付记录不完整，但不能掩盖或改变测试门禁结果。

### 2.6 交付卫生

- 完成 `git diff --check`，并通过适用的语法检查、类型检查、构建或 lint；
- `git status` 已检查，未把用户原有的本地修改误删、覆盖或混入交付；
- 变更文件、验证命令、结果、依赖安装、遗留问题和未纳入的本地变动已写入最终说明；
- 没有未解释的临时文件、调试输出、失败测试或未提交的生成物。

## 3. 按风险选择验证深度

| 变更类型 | 最低验证 |
| --- | --- |
| 纯文档 | Markdown/链接检查（如适用）和 `git diff --check` |
| 单元逻辑或参数解析 | 自动化单元测试、语法检查、边界输入测试 |
| 文件/rosbag 转换 | 最小真实结构夹具端到端测试、输入只读验证、输出重名/失败路径验证 |
| 公共接口或数据格式 | 兼容性测试、旧用法回归测试、README 示例复现 |
| 高风险数据或破坏性操作 | 明确 dry-run/备份/恢复策略，并进行独立人工复核 |

最低验证不是上限；风险较高时应增加真实数据、性能、并发或人工检查。

## 4. 标记 DONE 前的检查清单

```text
[ ] Issue 目标和验收标准已逐项核对
[ ] Issue 阶段已逐项完成，每阶段均有测试和通过记录
[ ] 代码边界、错误处理和输入保护已核对
[ ] tests/ 中已有或新增自动化测试
[ ] 适用的测试、语法检查、构建/lint 已在 VelaLoom 环境通过
[ ] 数据安全、输出重名和失败路径已验证（如适用）
[ ] README、DECISIONS.md、PROGRESS.md 已同步（如适用）
[ ] git diff --check 通过，git status 已检查
[ ] 已记录验证命令、结果、依赖、遗留问题和未纳入变动
[ ] 可执行模块文件头包含 Purpose/Input/Output/Example（如适用）
[ ] CHANGELOG.md 已记录本次特性或修复及其原因
[ ] 变更仅涉及一个模块，特性分支未提交，最终提交位于 main
[ ] 没有未解释的失败、跳过项或临时产物
```

只有清单中所有适用项完成，且不存在未披露的阻塞条件，Issue 才能从 `IN_PROGRESS` 改为 `DONE`。

## 5. 例外和阻塞规则

- 无法满足某项时，必须写明原因、影响、已尝试的替代验证和后续动作；
- 外部服务、硬件、超大数据或缺失依赖导致无法验证时，状态使用 `BLOCKED`，不能用“基本完成”代替；
- 用户明确接受风险后，可以交付带遗留项的结果，但必须在 Issue、进展记录和最终说明中显式标注，不得伪装成全部完成；
- 后续修复遗留项时应新增或恢复一个明确 Issue，并补齐相应测试。
