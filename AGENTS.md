# Project execution environment

- Run non-ROS project commands in the conda environment named `VelaLoom`.
- For non-interactive non-ROS commands, prefer `conda run -n VelaLoom <command>` so the environment is explicit and reproducible.
- An already activated `VelaLoom` environment is also acceptable for non-ROS work. Before relying on activation, verify that `CONDA_DEFAULT_ENV=VelaLoom`.
- ROS1/rosbag operations that require the ROS Noetic runtime must run inside the Docker container named `ros1_noetic`; this is the intentional exception to the conda rule.
- The `ros1_noetic` container is an execution environment only. Before use, verify its workspace mount with `docker inspect`; if it is stopped, start it, source `/opt/ros/noetic/setup.bash`, and use the container path corresponding to the mounted host workspace.
- ROS command outputs must be written through that mounted path so bags, logs, and generated files remain in the host workspace. Do not store required deliverables only in the container filesystem.
- Do not install project dependencies or execute non-ROS project tooling in `base`, another conda environment, or the system Python environment.

# Project layout

- Keep development code, scripts, tests, and other executable tooling outside the `urdf` and `rosbag` directories.
- Store shared project scripts in the repository-level `scripts/` directory.
- Treat `urdf` directories as robot description and model assets, and `rosbag` directories as recorded data only.

# Test output location

- Write every file generated by development testing or validation under the repository-level `test_output/` directory, using an Issue- or module-specific subdirectory.
- This includes generated fixtures, temporary bags, converted bags, logs, reports, screenshots, decision files, hashes, and intermediate outputs.
- Do not place test outputs in system temporary directories, paths outside the repository, `rosbag`, `urdf` directories, or source directories.
- ROS container test outputs must use the mounted path corresponding to the host repository's `test_output/` directory.
- Only clean exact subpaths created by the current test run; never recursively clear the entire `test_output/` directory.
